# security-review-sample-report-proof

An independent security review you can audit, end to end. A tiny synthetic multi-tenant API ships in
two versions: **v1** with eight planted weaknesses from the OWASP Top 10, and **v2** with every one
remediated. An automated review suite drives the app through its public HTTP surface, **finds** each
weakness on v1, **confirms it is closed** on v2, scores it with CVSS 3.1, and writes a redacted
sample report with a retest column.

Everything is synthetic, offline and deterministic. There is no real system, no client data, no
network, and no scanner: each finding is reproduced by one specific request sequence. The app is
seeded in memory, the "LLM feature" is a local stub, and the repo is MIT-licensed.

## What it proves

A review is only as good as its evidence. This one is itself tested:

1. **Every planted weakness is found on v1** — eight probes, one per item, each asserting the literal
   status and shape of the response (e.g. a Contoso token receives a Northwind record, HTTP 200).
2. **Every weakness is confirmed closed on v2** — the same eight probes, now blocked (403/404/400/401).
3. **Reverting a fix breaks the suite** — each file in [`footguns/`](footguns/) reverts exactly one
   v2 remediation; `npm run footgun <name>` passes only when exactly the tests named in
   [`footguns/manifest.json`](footguns/manifest.json) go red and every other test stays green.

So the suite does not just assert that v2 is safe — it demonstrates that it would notice if v2 stopped
being safe.

## Findings

CVSS 3.1 base scores are computed from the vectors in [`src/scoring.ts`](src/scoring.ts), not typed
in. The Retest column is the result of re-running each probe against v2.

| # | Finding | OWASP 2021 | Route | CVSS | Severity | Retest (v2) |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Broken object-level authorization (cross-tenant read) | A01 Broken Access Control | `GET /records/:id` | 6.5 | Medium | Closed |
| 2 | Broken function-level authorization (client-supplied role) | A01 Broken Access Control | `POST /admin/config` | 8.1 | High | Closed |
| 3 | Token accepted without full verification | A07 Identification and Authentication Failures | `GET /me` (all authed routes) | 9.1 | Critical | Closed |
| 4 | Inbound webhook integrity not enforced | A08 Software and Data Integrity Failures | `POST /webhooks/billing` | 7.5 | High | Closed |
| 5 | Path traversal on a file reference | A01 / A05 | `GET /files?name=` | 6.5 | Medium | Closed |
| 6 | Mass assignment of a protected field | A08 Software and Data Integrity Failures | `PATCH /records/:id` | 6.5 | Medium | Closed |
| 7 | Untrusted input reaches the model prompt | A03 Injection | `POST /assistant/summarize` | 5.4 | Medium | Closed |
| 8 | Missing security headers and CSRF posture | A05 Security Misconfiguration | `POST /records` | 4.7 | Medium | Closed |

Verdict on v1: 8 findings open (1 Critical, 2 High, 5 Medium). Verdict on v2: all closed. The full
measured report is [`SAMPLE_REPORT.md`](SAMPLE_REPORT.md) (regenerated by the `review` command).

Each remediation is the standard control: ownership check (1); server-side role from the verified
token (2); full token verification with `jose` — signature, audience, issuer, expiry (3);
HMAC-SHA256 signature over timestamp+body compared in constant time, with a replay window (4);
path normalization and confinement (5); a writable-field allowlist (6); instruction/data separation
for the stub (7); security headers plus same-origin and a CSRF token (8).

## Run it

Node 22.12 or later (declared in `engines`; developed on Node 24). No Docker, no database, no API key.

```bash
npm ci
npx tsc --noEmit
npm test                      # 30 tests: 8 v1 probes, 8 v2 probes, CVSS, report, LLM stub
npm run review -- v1          # writes SAMPLE_REPORT.md for v1 (findings open)
npm run review -- v2          # writes SAMPLE_REPORT.md for v2 (all closed)
npm run footgun revert-object-auth   # revert one v2 fix; the suite must bite
```

## The suite bites: footguns

| Footgun | What it reverts | Tests that must fail |
| --- | --- | --- |
| `revert-object-auth` | ownership check on `GET /records/:id` | `(b1)`, `(d2)` |
| `revert-function-auth` | server-side role check on `POST /admin/config` | `(b2)`, `(d2)` |
| `revert-token-check` | full token verification (back to decode-only) | `(b3)`, `(d2)` |
| `revert-webhook-verify` | webhook signature + replay window | `(b4)`, `(d2)` |
| `revert-path-confine` | path normalization/confinement | `(b5)`, `(d2)` |
| `revert-field-allowlist` | writable-field allowlist | `(b6)`, `(d2)` |
| `revert-prompt-separation` | instruction/data separation | `(b7)`, `(e)`, `(d2)` |
| `revert-headers` | security headers + CSRF/same-origin | `(b8)`, `(d2)` |

The mapping is **measured, not guessed**: it was produced by running each footgun and recording what
went red. `(b1)`..`(b8)` are the per-item "closed on v2" assertions; `(e)` is the LLM-stub output
test; `(d2)` is the aggregate retest assertion ("v2 report lists 8 retests all Closed"), which goes
red the moment any fix is reverted. The tests are never edited to fit the manifest.

## Methodology (what a review of your API would deliver)

This repo is shaped to answer what security clients actually ask for:

- **"An independent engineer to review it, then retest what we fix."** The review is a separate suite
  that drives the app from the outside; the retest is the same suite re-run against the fixed version
  (the Retest column, and `npm run review -- v2`).
- **"Findings ranked by severity, each with steps to reproduce and a recommended fix."** Every finding
  carries a CVSS 3.1 severity, the exact route and observed response that reproduces it, and a
  remediation.
- **"Each finding with CVSS severity, evidence and remediation."** The report has one row per finding
  with all three; evidence is the measured HTTP response, not a description.
- **"A retest of every Critical and High fix."** All eight fixes are retested; the Critical/High ones
  (items 2, 3, 4) are included.
- **"A redacted / anonymised sample report."** `SAMPLE_REPORT.md` uses synthetic tenant names and no
  real hosts — it *is* the redacted sample.
- **"An automated scan alone will not be accepted: we need manual testing."** There is no scanner here.
  Each probe is a hand-written request sequence targeting one class of flaw, the way manual testing
  works; the automation is only the harness that re-runs them.

## Limitations, stated plainly

- **Synthetic app and data.** The target is a seeded in-memory API built to carry these eight
  categories; it is not a real service and has no real users or hosts.
- **The planted set is finite.** A review finds what it checks. Eight items were planted and eight
  are found; this is a demonstration of method, not an exhaustive catalogue of a real system.
- **CVSS scores are illustrative.** The vectors are a reviewer's judgement on a synthetic target; on a
  real system, environmental and temporal metrics would apply.
- **Offline LLM stub.** The "model" is a deterministic local function, so the injection item is shown
  at the prompt-construction boundary, not against a real model.
- **HTTP-layer only.** Security headers and CSRF are demonstrated at the HTTP layer; no browser, no UI.
- **No real run.** Nothing here was run against any third party, and the probes only hit this repo's
  own in-process app.

Third-party claims (CVSS 3.1 definitions, OWASP ids, `jose` semantics, webhook-signature practice)
are quoted from official pages in [`docs/sources.md`](docs/sources.md), or marked "not verified".

## Layout

```text
src/scoring.ts              CVSS 3.1 weight table + base-score computation + per-finding vectors
src/app/                    the shared shell: routes, seed, tokens, LLM stub, config, types, fixtures
src/app-v1/controls.ts      the eight planted weaknesses (one function per item)
src/app-v2/controls.ts      the eight remediations, parallel in shape
src/review/                 probes (one per finding), run harness, findings metadata, report generator
src/cli.ts                  npm run review -- v1|v2
test/                       probe suite (a/b), CVSS (c), report (d), LLM stub (e)
footguns/                   one patch per remediation + manifest of the tests it must fail
scripts/footgun.mjs         apply, run, revert, strict verdict
```
